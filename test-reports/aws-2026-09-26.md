Region eu-central-1 (Frankfurt). Clients on EC2 t3.micro (Amazon Linux 2023, Corretto 25) in
the same region. No password, key or token appears in this log; the IAM tokens were built by

## Aurora PostgreSQL 17.9 (express configuration: writer + reader, serverless v2)

| Check | Result |
|---|---|
| Login with an IAM token built off the heap, TLS verify-full | ok (`writer before: seclume-apo-instance-1 (writer)`) |
| `targetServerType=secondary` with `aurora=true` | ok (`seclume-apo-instance-2 (reader)`) |
| `tlsRootCert=aws-rds` | ok after fix 2 |
| Real failover (`aws rds failover-db-cluster`), new connections every 500 ms until the new writer answers | **32 260 ms** with `aurora=true`, **32 572 ms** without |

Honest reading of the failover numbers: in the express configuration the cluster endpoint and
the instance endpoints resolve to the same relay addresses, so there is no stale DNS name to
route around - both clients wait for Aurora's promotion itself. `aurora=true` followed the
topology correctly; a speed advantage needs a cluster whose endpoints are ordinary DNS names
(not available on the free plan).

## Cross-host session mobility on three EC2 machines (splice mode)

R = splice node + PostgreSQL 17 (TLS), A and B = members; ordinary user processes, no
rights. Private network 172.31.0.0/16.

| Test | Result |
|---|---|
| Bound sessions: request on A, next on B, back to A | same backend (pid 35785), the uncommitted row travelled, committed on B, logout forgotten on both |
| **Real crash**: A stopped with `aws ec2 stop-instances --force` | B carried the same session on (pid 35891) about 5 s later, the row A wrote committed on B |
| **Real network partition**: A cut off with nftables (checked: A cannot reach B) | B carried the session on from its copy and wrote a second row; A, back, recognised the takeover, wrote nothing, took the session over from B; both rows committed |
| The same three with **PostgreSQL and RDS MySQL together** | all green: bound (pg pid 37737, MySQL connection 35), crash (37785 / 40), partition (38022 / 45) |

A first partition run was discarded: nftables was not installed on A, so A was never cut off
and the session moved by an ordinary handover. The runs above were made after checking that A
could no longer reach B.

R holds the only TUN device (root, `ip tuntap`) and routes; A and B are ordinary processes as
uid 1000 with `CapEff: 0000000000000000` - no device, no rights. The connection runs on
seclume's user-space TCP inside a mutually authenticated tunnel to R.

| Database | Result |
|---|---|
| PostgreSQL 17 (on R) | moved A -> B: same backend (39532), auto-commit off and SERIALIZABLE kept, the two uncommitted rows there and still invisible to others, committed on B |

Setup notes, not findings: PostgreSQL on R needed a `pg_hba` entry for the tunnel network, and
the RDS MySQL is reached through a forward on R (the tunnel carries a member's traffic to R,
as in the home lab where all databases sit on one host). One run failed on a security group
that did not open the forward's port; not counted.

## AWS Secrets Manager and the EC2 instance role

| Check | Result |
|---|---|
| `provider=aws-secrets-manager&field=password` with a key pair, secret in RDS's JSON shape | ok after fix 7: `seclume_test@% by caching_sha2_password, TLSv1.3` |
| **No key anywhere** - `credentials=instance`: the EC2 instance role's temporary credentials from IMDSv2, secret key and session token read into native memory | new, built today |
| RDS MySQL IAM login with `credentials=instance` (the token carries the role's session token, signed and sent) | ok: `iamuser@% by mysql_clear_password` |
| Secrets Manager with `credentials=instance` | ok: `seclume_test@% by caching_sha2_password` |

The IAM token with a session token could not be compared byte for byte with the AWS CLI's: the
CLI fetched a credential set of its own, and the session tokens differ from the first
character on. Its validity is what the login shows - RDS accepted it.

Found while building it: `rds-iam` could not use temporary credentials at all, and it put the
finished token - the database password for fifteen minutes - into a `String` before writing
it out, although its documentation said it did not. The token is now written into native
memory directly, with or without a session token.

## What was torn down

All of it, the same day: the Aurora cluster and its two instances, RDS MySQL, RDS SQL Server,
four EC2 instances, the secret, the key pair, the security group. The AWS key used for the run
was held only in RAM on the test host and shredded afterwards.
